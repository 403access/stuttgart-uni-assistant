# Localization

Every user-facing string is looked up by key. No screen carries a German and an
English copy of the same sentence inline. German is the source language and the
source of truth for the key set; English is a full second set, not a machine
pass left in the bundle.

## Files

| File | Role |
| --- | --- |
| `apps/mobile/src/i18n/de.ts` | The German catalog. Every key in the app is defined here, and `TranslationKey` is derived from it |
| `apps/mobile/src/i18n/en.ts` | The English catalog, typed `Record<TranslationKey, string>` so the compiler fails when a key is missing or extra |
| `apps/mobile/src/i18n/index.ts` | The lookup: `tx(locale, key, values?)` |
| `apps/server/i18n/de.mjs`, `en.mjs`, `index.mjs` | The same pattern for the assistant server's copy |

`apps/mobile/src/text.ts` re-exports `tx` (and a `t` alias) so existing imports keep working;
new code can import from `@/src/i18n`. The locale-aware formatters stay in
`apps/mobile/src/text.ts` (`formatDate`, `formatDay`, `formatTime`, `formatGrade`,
`weekdays`, `shortMonths`).

## Calling it

```ts
tx(locale, 'calendarHero.anstehende');            // no values
tx(locale, 'calendarHero.anstehende', [count]);   // 10 anstehende Termine
```

Values are positional and fill the `{0}`, `{1}`, … placeholders in the catalog
value. A value is a `string`, a `number`, or `undefined`. The locale argument is
the `Locale` from `useAppSelector((state) => state.locale)` (`@/src/types`).

`tx` never falls back to a literal sentence: the key type is a union of every
key in `de.ts`, so an unknown key is a type error rather than a runtime miss.

## Keys

A key is `namespace.slug`.

- **Namespace** names the file or feature the string belongs to, derived from its
  path (`apps/mobile/app/(tabs)/kalender.tsx` → `tabsKalender`, `apps/mobile/src/components/calendar-hero.tsx`
  → `calendarHero`). A string used in more than one file is hoisted to `common`.
- **Slug** is the shortest unique prefix of the significant words of the German
  text (`anstehende_termine` → `anstehende` when no sibling collides).

Keys are stable identifiers; edit the values, not the keys. Namespaces keep a
slug short and unique, so renaming a string never has to touch a key.

## Adding or changing a string

1. Add the key to `apps/mobile/src/i18n/de.ts` with the German value and to `apps/mobile/src/i18n/en.ts`
   with the English value. Use `{0}`, `{1}`, … for anything dynamic.
2. Call `tx(locale, 'key', [values])` where the text is shown.
3. `npm run check` type-checks the two catalogs against each other.

Do not reintroduce `tx(locale, 'Deutsch', 'English')` pairs: type checking
rejects the literal as a key, and it is what this module exists to replace.

## Content versus copy

The `Localized` type (`{ de, en }`) is still used, but only for **content** in
`apps/mobile/src/data/`: module titles, summaries, place notes, document pages, deadlines.
Those are read with `pick(value, locale)` and are deliberately not keys, because
they are the fictional record itself, not interface copy. Interface labels,
buttons, notices, and generated answer text all go through `tx`.

## The assistant

`apps/mobile/src/assistant/answer.ts` and `apps/mobile/src/assistant/context.ts` build the answers with
`tx`, so the same catalog drives both the local answers and every transcript.
The server's system prompt is keyed in `apps/server/i18n/` and selected with
`t(locale, 'assist.systemPrompt')`.
